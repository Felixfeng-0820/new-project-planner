# Ideation and coaching

Use this reference only when the user has no project direction, asks for deeper teaching, or requests a retrospective.

## Direction finder

Ask three questions in one batch:

1. What repeated problem have you, your family, classmates, or coworkers faced recently?
2. What is the goal: learn, build a portfolio piece, save time, support research, earn money, or enter a competition?
3. Who is the first real user, and what would they do with the result next week?

Recommend no more than three directions. For each, include:

- problem and first user;
- smallest useful v1;
- likely project profile(s);
- evidence that would prove usefulness;
- one upgrade path after feedback;
- major cost, data, or platform constraint.

Prefer problems supported by repeated manual work, direct access to a first user, or multiple independent complaints. Do not research indefinitely: choose a testable direction, build a small release, and collect real feedback.

## Broader project shapes

Use these as prompts, not a fixed catalog:

- a CLI that safely removes repetitive file or data work;
- an API that turns a manual workflow into a reusable service;
- a local-first web or desktop tool for sensitive personal data;
- a data pipeline and baseline model with reproducible evaluation;
- an AI assistant with a small representative quality test set;
- a library that packages a useful algorithm behind a clean public API;
- a mobile utility that works offline and uses one platform capability well;
- an internal automation with dry-run, idempotency, and an audit trail;
- a public-data product with provenance, caching, and graceful failures;
- an extension or integration that improves an existing daily tool.

## Teaching after a slice

Use at most four short lines:

1. **Built** — the user-visible result.
2. **Why** — the key design choice.
3. **Concept** — one new term in plain language.
4. **Evidence** — the exact check and its scope.

Do not explain every file or repeat concepts already covered. Offer depth only when it helps the user make the next decision or they ask for it.

## Explain a concept

When the user asks for teaching:

1. define the concept in plain language;
2. explain the problem it solves;
3. connect it to the current project with one concrete example;
4. give one small practice task;
5. ask two short understanding questions if the user wants a quiz.

Prefer concrete values and behavior before formulas or abstractions.

## Retrospective

At project or milestone completion, summarize:

- three important things the user can now explain or repeat;
- one decision that worked and the evidence behind it;
- one mistake, limitation, or uncertainty to handle differently next time;
- one skill to practise in the next project;
- the smallest next release, only if the user wants to continue.

Separate what the agent implemented from what the user personally did. Do not turn team or agent work into an unsupported résumé claim.
