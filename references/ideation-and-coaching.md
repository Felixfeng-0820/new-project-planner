## Student launchpad

Use this path when a student or first-time builder has mostly coursework, feels behind after seeing other people ship or earn, or wants a portfolio, freelance pilot, or first income experiment but cannot name a concrete problem.

Do not begin with a framework choice or a list of supposedly profitable app ideas. First identify one primary goal: learn by shipping, create credible portfolio evidence, save someone's time, test willingness to pay, or support research or a competition. Treat income as an experiment outcome, not a guaranteed feature.

Recommend a default first bet with these properties:

- one reachable first user from the user's classmates, student group, lab, family, community, or a familiar small organization;
- one repeated and observable job, not a broad audience persona;
- zero or near-zero spend, no sensitive real data in early tests, and no public deployment unless it helps the next evidence gate;
- a useful v1 that can be tested in roughly three to seven focused work sessions;
- one skill stretch for the student, while the rest uses familiar or low-complexity tools.

Move through three evidence gates and name them separately:

1. **Problem evidence** — a repeated task, direct complaint, or observed workaround exists.
2. **Use evidence** — the first user can complete the core job and chooses to use the result again.
3. **Payment evidence** — the user explicitly accepts or rejects a price, deposit, or small paid pilot and explains why. Praise, page views, and a finished website do not count.

If earning is a goal, include how the student can reach the first customer and a small price or pilot hypothesis before adding growth features. The student controls outreach, payments, and public claims; apply the normal authority gates to any external message, account, payment, or deployment. A website is a delivery surface, not a business model.

Peer success stories, online complaints, competitor searches, traffic, praise, and survey intent generate hypotheses only. Check the current workaround, frequency, cost, and actual behavior. Prefer a concierge service, manual test, local demo, or small private pilot when it can produce the next signal more cheaply than a full build. Deploy only when deployment itself enables that signal; pivot or stop when evidence is weak instead of adding features.

Do not force a learning or portfolio project to prove a commercial market. Its valid outcomes may instead be real technical evidence, honest attribution of the student's contribution, one user's feedback, and a project the student can explain and extend.

## Direction finder

Ask at most three brief questions; use one batch only when the user can answer them easily:

1. What is the primary goal: learn, build a portfolio piece, save time, support research, test willingness to pay, or enter a competition?
2. Which contexts can the user observe directly: their own study, dorm, student group, lab, family work, internship, part-time work, or another familiar setting?
3. Which three to five people can they reach this week, and what repeated behavior or workaround could be observed?

If the user cannot answer, do not continue an open-ended interview. Make the smallest disclosed assumptions, offer two or three candidates across different project profiles, and recommend one default.

Recommend no more than three directions. For each, include:

- problem and first user;
- smallest useful v1;
- likely project profile(s);
- cheapest manual or pre-build test and its go/no-go signal;
- evidence that would prove usefulness;
- for an earning experiment, a reachable first-customer path and the next payment-evidence gate;
- one upgrade path after feedback;
- major cost, data, or platform constraint.

Prefer problems supported by repeated manual work, direct access to a first user, or multiple independent complaints. Do not rank ideas mainly by technical novelty, prestige, or hypothetical market size. Do not research indefinitely: choose a testable direction, build a small release, and collect real feedback.

## Broader project shapes

Use these as prompts, not a fixed catalog:

- a CLI that safely removes repetitive file or data work;
- an API that turns a manual workflow into a reusable service;
- a local-first web or desktop tool for sensitive personal data;
- a data pipeline and baseline model with reproducible evaluation;
- an AI assistant with a small representative quality test set;
- a library that packages a useful algorithm behind a clean public API;
- a mobile utility that works offline and uses one platform capability well;
- an internal automation with dry-run, idempotency, and an audit trail;
- a public-data product with provenance, caching, and graceful failures;
- an extension or integration that improves an existing daily tool.

## Teaching after a slice

Use at most four short lines:

1. **Built** — the user-visible result.
2. **Why** — the key design choice.
3. **Concept** — one new term in plain language.
4. **Evidence** — the exact check and its scope.

Do not explain every file or repeat concepts already covered. Offer depth only when it helps the user make the next decision or they ask for it.

## Explain a concept

When the user asks for teaching:

1. define the concept in plain language;
2. explain the problem it solves;
3. connect it to the current project with one concrete example;
4. give one small practice task;
5. ask two short understanding questions if the user wants a quiz.

Prefer concrete values and behavior before formulas or abstractions.

## Retrospective

At project or milestone completion, summarize:

- three important things the user can now explain or repeat;
- one decision that worked and the evidence behind it;
- one mistake, limitation, or uncertainty to handle differently next time;
- one skill to practise in the next project;
- the smallest next release, only if the user wants to continue.

Separate what the agent implemented from what the user personally did. Do not turn team or agent work into an unsupported résumé claim.
